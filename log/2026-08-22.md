# Build log #1 — 3 to 22 August 2026

Starting a weekly log. This first entry backfills three weeks, to keep a structured sequence.

---

## What this was

I wanted to know whether putting a canary token in an LLM agent's tool registry would actually be useful. The age-old idea is demonstrably sound in typical security surfaces. Leave something in the environment that nothing legitimate ever touches, and every time it gets touched you have a real alert with no false positives. It made sense that agents connected to internal tools looked like a surface where that would work.

It all depends on one number nobody had measured: how often does a benign agent touch the decoy anyway?

So I measured it. Then the measurement turned into something more interesting than the thing I set out to build.

---

## 3 August — baseline

101 benign engineering prompts, three decoy variants, ten runs each. 3,030 trials against `claude-sonnet-4-6`.

Result: 0%, 0.30%, 0.59%. Low, as hoped.

Except all nine positive trials came from a *single* prompt out of 101:

> Get the status page contents for our CDN provider.

The other 100 prompts produced zero hits across 3,000 trials.

I read a trend into the three variant rates and drew a conclusion about decoy attractiveness. That conclusion was wrong, for reasons I get to below.

---

## 8 August — is it one prompt or a class?

If one prompt in a hundred does this, it's a curiosity. If it belongs to a class of prompts, it's a finding.

Twelve matched pairs — same task, same verb, only the referent changed. "our CDN provider" versus "Cloudflare". 840 trials.

Unresolved referent: 18.61%. Named vendor: 0%. Eleven of twelve pairs fired.

A class, then.

Same day I noticed the design had a confound. "Cloudflare" does two things at once: it disambiguates *which* provider, and it names something the model already knows about. Those are different variables and I'd collapsed them.

So I added a third condition — a vendor that is unambiguously named and completely fictional. "Northbrook CDN." 1,200 trials per model, on two models. That separated it. Both components contribute, and the split differs by model.

---

## 12 August — does it generalise?

Two studies on one vendor's models is not a finding about LLM agents. It's a finding about one vendor.

Cross-vendor harness: six models, two vendors, flagship / balanced / lightweight tier from each. Model selection rule fixed before I looked at any results. 7,200 trials.

It replicated in five of six models.

The sixth was the interesting one. `claude-opus-5` recorded a single decoy invocation across 720 ungroundable trials. Essentially immune.

A third vendor was attempted and abandoned — every candidate model returned plan-level quota errors. That's in the limitations, not hidden.

## 19 August — the statistics were wrong

This is the part I'd rather not write, which is why it's worth writing.

Every p-value in my draft treated each trial as an independent observation. They aren't. Ten runs of the same prompt are ten measurements of one prompt, not ten independent samples. That's pseudo-replication, and it makes p-values far too small.

The effect is severe in this data because hits concentrate inside prompts. In the baseline study, all nine positives came from one prompt out of 101.

Recomputed with the prompt as the unit of analysis:

| | Trial-level | Prompt-clustered |
|---|---|---|
| Attractiveness trend | p = 0.0142 | **p = 0.385** |
| Study 2 headline | p = 4.6 × 10⁻²² | **p = 9.8 × 10⁻⁴** |

**The finding survives.** Five of six models remain significant under a cluster permutation test, with matched controls at zero throughout. What doesn't survive is the exponents — 10⁻²² was never supportable from twelve prompt triples, and a signed-rank test on twelve pairs cannot produce anything below about 5 × 10⁻⁴ no matter how large the effect. That limit is now stated in the paper.

The attractiveness trend from 3 August was never real. At the prompt level it's 0, 1 and 1 hitting prompts out of 101. I withdrew it.

## 19 August — the result I nearly missed

While checking whether an alternative explanation held, I ran an analysis I hadn't planned, and it turned out to be the strongest thing in the dataset.

The obvious objection to all of this is: maybe the decoy fires because no legitimate tool serves the request. So I checked what the agents actually called.

Proportion of trials invoking `fetch_url` — the tool that legitimately answers these requests:

| Condition | Rate |
|---|---|
| Entity named and familiar | **78.1%** |
| Named but unfamiliar | 15.1% |
| Unnamed referent | **5.0%** |

Same gradient in all six models, including the immune one.

The correct tool isn't missing. It's used correctly the overwhelming majority of the time — right up until the agent can't ground the entity, at which point it becomes unusable, because you cannot fetch a URL for a provider you cannot name. The agent then substitutes internal search, and reaches a configuration-export tool on the way.

That turned the mechanism from something I was arguing for into something I could show.

## 20 August — reframing

The paper had been written as a security paper: decoy tools as a defensive primitive, false-positive rates, detection.

But the strongest result isn't about defence. It's about reliability — what a tool-using agent does when the tool it correctly identified turns out to be unusable. The decoy isn't a tripwire in this telling; it's a *measurement instrument*, a way to observe misselection without needing a ground-truth answer for every call.

Retitled, restructured, and repositioned against the function-calling evaluation literature rather than the agent-security literature. Decoy placement is now a corollary rather than the headline.

Also tested and rejected the obvious reading of the immune model's behaviour. It doesn't avoid the decoy by declining to act — it has a 0.0% zero-tool rate and averages 2.04 tool calls per trial. It runs internal search instead, correctly. What's been trained away isn't caution. It's reaching for the wrong instrument when uncertain.

## 22 August — shipped it as a tool

A paper tells you a number about my synthetic ten-tool catalogue. That's not much use to anyone running agents in production.

So the harness is now a package:

```
pip install ungrounded
ungrounded run --model claude-sonnet-4-6
```

Zero required dependencies. It ships the paper's twelve prompt triples verbatim and its ten-tool catalogue, so a zero-argument run reproduces the study; point it at your own catalogue and it measures your agent instead. The prompt-clustered inference is built in, and every summary prints the smallest p-value the design can produce, so nobody can accidentally quote an exponent their sample size doesn't support.

Then I ran it across six models at 20 runs per cell — 1,440 trials each — and published the leaderboard.

**It replicated the paper.** Correct-tool usage landed within a few points of Study 4 on every model, the ordering was preserved, and `claude-opus-5` came out null in both. An independent implementation, a different SDK generation, three rewrites of the provider adapter in one afternoon, and the numbers held.

Two things I learned building it that aren't in the paper. Provider SDKs reject arguments in two entirely different ways — a `TypeError` before the request goes out, or a 400 afterwards — and one OpenAI model refuses function tools altogether unless reasoning effort is set to none. The tool now reads the remedy out of the error message and adapts. And run-to-run variance is larger than I'd assumed: four identical runs gave a twelve-point spread on the decoy rate, though correct-tool usage moved less than three. That's in the README, because a user seeing a different number on their second run should know it's sampling, not a bug.

## 22 August — I published my own API keys

Worth recording properly.

Bumping a version, I ran `git add -A` in a directory containing a `.env` file. GitHub's push protection blocked the commit — working exactly as designed. But `python -m build` had already packaged the same working tree, and that sdist went to PyPI with both my Anthropic and OpenAI keys inside it.

Caught it within a few minutes, rotated both keys, deleted the release. No unexpected billing on either account.

Three things went wrong and all three are worth naming. `.gitignore` doesn't control what a build backend packages, which I'd assumed it did. A credentials file inside a directory you both commit and package is a standing hazard, not a convenience. And `git add -A` is the wrong command in any repo where a mistake is public.

Fixed: explicit sdist allowlist so nothing new can leak by default, credentials moved out of the repo entirely, and a check on the tarball contents before every upload.

I'd rather have this in the log than not. Anyone reading a project that publishes its own retractions should also see the operational mistakes.

## Where it stands

Four studies. 13,470 trials. Six models, two vendors. Three of my own hypotheses retracted with the data that overturned them. Everything public, everything reproducible from raw data with one command, and now installable.

Twenty days.

**Next:** the mechanism predicts that adding a tool which resolves internal vendor references should restore correct routing and silence the decoy. That's a direct test and it's the obvious next experiment.

The open question I can't answer alone is whether any of this survives contact with a production tool catalogue. Mine is synthetic. If you're shipping agents and you run it, I'd like to know what came back — or send me your tool schema and five representative requests and I'll run it for you.
